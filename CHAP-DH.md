# CHAP-DH Technical Document

## Anonymous IEM Chain Protocol with DH Key Exchange

> **NOTE: This protocol is NOT the legacy Challenge-Handshake Authentication Protocol (CHAP).** This is a completely different protocol family. CHAP-DH is an anonymous variant of CHAP-IEM based on Diffie-Hellman key exchange.

---

## I. Overview

CHAP-DH is an anonymous variant of the CHAP-IEM protocol. It removes the login phase and replaces it with DH key exchange.

| Comparison Dimension | CHAP | CHAP-IEM | CHAP-IEM-SKN | **CHAP-DH** |
|---------------------|------|----------|--------------|-------------|
| Pre-shared Secret | Required (password) | Required (password) | Required (Y) | **Not required** |
| Login Phase | Yes | Yes | Yes | **No (replaced by DH exchange)** |
| Authentication | Yes | Yes | Yes | **No (anonymous)** |
| Server Key Table | Required | Required | Required | **Not required** |
| ID₁ Generator | Server | Server | Server | **Either party (client recommended)** |
| IEM Chain | Yes | Yes | Yes | Yes |
| Forward Secrecy | Not supported | Supported | Supported | Supported |
| Offline Brute Force Risk | Yes | Yes | None | **None** |

---

## II. Core Principle

### 2.1 Design Philosophy

CHAP-DH is essentially: **replace the login phase of CHAP-IEM with DH key exchange**.

- Purpose of login phase: establish initial shared key K and distribute ID₁
- Purpose of DH exchange: establish initial shared key K
- Distribution of ID₁: encrypted with K, can be initiated by either party

Removing the login phase means:
- No username
- No password
- No pre-shared secret
- Completely anonymous

### 2.2 Color Analogy

```
No pre-shared secret

Client                               Server
   |                                  |
Private random: Red                   Private random: Blue
   |                                  |
Orange = g^Red                        Green = g^Blue
   |                                  |
   |-------- Send Orange ------------→|
   |←------- Send Green -------------|
   |                                  |
Brown = Green^Red                     Brown = Orange^Blue
   = g^(Red×Blue)                      = g^(Red×Blue)
   |                                  |
   └────────── Same Brown ────────────┘

Brown is the shared key K
```

### 2.3 Optional ID₁ Initiator

Unlike CHAP-IEM, ID₁ in CHAP-DH can be generated and initiated by **either party**:

| Initiator | Flow | Use Case |
|-----------|------|----------|
| Client | Client generates ID₁ → sends encrypted with K → Server decrypts and confirms | Default recommendation |
| Server | Server generates ID₁ → sends encrypted with K → Client decrypts and confirms | Server-initiated session establishment |

**Client initiation is recommended**, as the client typically has better knowledge of its own session requirements.

## III. Complete Workflow

### 3.1 Key Exchange Phase

Neither party requires any pre-shared secret.

The client generates a cryptographically secure random number `a` and computes `A = g^a mod p`, then sends `A` to the server.

The server generates a cryptographically secure random number `b` and computes `B = g^b mod p`, then sends `B` to the client.

Upon receiving each other's messages, both parties compute the shared key `K`:

- Client: `K = B^a mod p`
- Server: `K = A^b mod p`

At this point, both parties have the same session key `K`.

### 3.2 ID₁ Distribution Phase (Client-Initiated Mode)

The client generates a cryptographically secure random number `ID₁`, encrypts it with `K`, and sends it to the server:

```
Client → Server: Init Packet = AES256_K(ID₁)
```

The server decrypts with `K`, obtains `ID₁`, and sets it as the current valid ID.

The server may return any content (token, ID₂, push message, etc.) encrypted with `ID₁`:

```
Server → Client: Response Packet = AES256_ID₁(any_data + ID₂)
```

Where:
- `any_data` can be a token, confirmation, push message, or anything else
- `ID₂` is the next ID generated by the server

The client decrypts with `ID₁`, obtains the server's data and `ID₂`, then updates its current encryption key to `ID₂`.

**Key characteristics**:
- The response packet does not have to be "OK"
- May contain any data the server wishes to push
- The first response already enables bidirectional communication

### 3.3 ID₁ Distribution Phase (Server-Initiated Mode)

The server may also initiate:

```
Server → Client: Init Packet = AES256_K(ID₁)
```

The client decrypts with `K`, obtains `ID₁`, and sets it as the current valid ID. The client then encrypts a response with `ID₁` and returns it:

```
Client → Server: Response Packet = AES256_ID₁(any_data + ID₂)
```

### 3.4 Normal IEM Operation Chain

Subsequent operations are identical to CHAP-IEM.

Either party uses the current `IDₙ` as the AES256 key to encrypt data and sends it to the other party. The recipient decrypts with the same `IDₙ`, executes the operation or processes the message, generates a new random `IDₙ₊₁`, packages the result with the new ID, encrypts with `IDₙ`, and returns it.

The recipient decrypts with `IDₙ`, obtains the result and `IDₙ₊₁`, then updates its current encryption key to `IDₙ₊₁`.

Each subsequent interaction repeats this process, forming a key chain: `ID₂ → ID₃ → ID₄ → ...`

### 3.5 Bidirectional Push

Since ID₁ can be initiated by either party, CHAP-DH natively supports bidirectional communication:

- **Request-Response Mode**: One party initiates a request, the other replies
- **Push Mode**: Either party actively sends data; the recipient decrypts and advances the ID chain

The push packet format is identical to a normal message packet: encrypted with the current `IDₙ`, containing both the actual data and `IDₙ₊₁`.

### 3.6 Exception Recovery

When a response packet is lost, causing the parties to become out of sync:

One party sends a message using what it believes to be the current `IDₙ`. The other party successfully decrypts but finds that `IDₙ` is no longer valid (already destroyed).

The party that detects the out-of-sync condition must use the recovery key to send synchronization information. In CHAP-DH, the recovery key is the DH-negotiated `K` (which should be retained for exception recovery).

**Recovery flow**:
1. The detecting party sends a recovery packet encrypted with `K`, containing the current valid ID and a sync instruction
2. The other party decrypts with `K`, obtains the current valid ID, and updates its local state
3. A confirmation packet is sent
4. Normal communication resumes

If `K` has been discarded, both parties must re-execute the complete DH exchange and ID₁ distribution process.

## IV. Engineering Practice Specifications

### 4.1 Parameter Specifications

| Parameter | Specification | Description |
|-----------|---------------|-------------|
| p (modulus) | 2048-4096 bits | Public parameter, can be hardcoded |
| g (generator) | Typically 2 or 5 | Public parameter, can be hardcoded |
| a, b (random numbers) | 256 bits | MUST use CSPRNG |
| K (DH shared key) | Same magnitude as p | Recommend deriving AES key via KDF |
| IDₙ | 256 bits | MUST be random, updated per interaction |
| AES key | 256 bits | All AES operations use AES-256 |

### 4.2 Handling of Public Parameters

`g` and `p` can be hardcoded in both client and server code, eliminating the need for network transmission during initial parameter negotiation. This prevents parameter downgrade attacks.

### 4.3 K Processing

The DH exchange yields `K` as a modular exponentiation result. It is recommended to derive a fixed-length AES key via a KDF (e.g., HKDF):

```
K_aes = HKDF-SHA256(K, "chap-dh-session")
```

### 4.4 Server State Management

CHAP-DH is a **stateful** protocol:

- The server must maintain the current valid ID for each client
- However, it does **not** need to maintain a user key table (no pre-shared secrets)
- The cost of maintaining per-session state is far lower than decrypting and verifying during login

| Operation | SKN (with login) | CHAP-DH |
|-----------|------------------|---------|
| Session establishment | Lookup key table + decrypt verify | DH exchange (modular exponentiation) |
| Per interaction | No table lookup | No table lookup |
| Server state | Session ID | Session ID |

### 4.5 Performance Comparison

| Scenario | SKN | CHAP-DH |
|----------|-----|---------|
| First session establishment | Table lookup + AES decrypt | DH modular exponentiation |
| Subsequent operations | O(1) state lookup | O(1) state lookup |
| Multi-user key table | Required (O(N) space) | **Not required** |
| New user configuration | Requires pre-shared Y | **Zero configuration** |

## V. Security Analysis

### 5.1 Offline Brute Force Resistance

CHAP-DH completely eliminates offline brute force risk:

- No password involved
- No pre-shared secret
- `K` comes from DH exchange, with no enumerable target

### 5.2 Forward Secrecy

Each session independently generates new `a` and `b`:

- `K` is used only for the current session
- The ID chain itself also provides forward secrecy (old IDs cannot derive new IDs)
- Even if a future session's `K` is compromised, other sessions remain unaffected

### 5.3 Anonymity

CHAP-DH transmits no identity information:

- No username
- No certificate
- No identifiable information whatsoever

### 5.4 Man-in-the-Middle Attacks

Standard DH does not resist MitM attacks. As CHAP-DH is positioned for anonymous communication, options include:

| Approach | Description |
|----------|-------------|
| Out-of-band verification | User manually compares key fingerprints |
| Trust on First Use (TOFU) | Record on first connection, verify subsequently |
| Accept risk | Acceptable in anonymous scenarios |

### 5.5 Replay Attacks

- DH exchange itself resists replay (each `a`, `b` is independently random)
- The IEM chain naturally resists replay (IDs are single-use)

## VI. Multi-User Scenario Analysis

### 6.1 Comparison with SKN

| Scenario | SKN | CHAP-DH |
|----------|-----|---------|
| Single user configuration | Requires pre-shared Y | **No configuration** |
| 200 users configuration | 200 Y values, key table required | **0 configuration** |
| New user | Requires assigning Y | **Plug and play** |
| User enumeration attack | Possible | **Not applicable (no user concept)** |
| Server storage | Key table + session state | Session state only |

### 6.2 Typical Application Scenarios

**IoT Sensor Networks**

- Hundreds or thousands of sensors need to connect to a gateway
- Pre-configuring independent keys for each sensor is impractical
- CHAP-DH allows sensors to work plug-and-play

**Temporary Anonymous Access**

- Guest WiFi
- Temporary device pairing
- One-time secure channels

**Server Horizontal Scaling**

- No need to share key tables
- Session affinity optional
- Restarting does not affect other sessions

## VII. Relationship with CHAP-IEM

CHAP-DH is a variant of CHAP-IEM:

```
CHAP-IEM = Login Phase (pre-shared K + server-generated ID₁) + IEM Chain
CHAP-DH   = DH Exchange (no pre-shared secret) + IEM Chain (client or server generates ID₁)
```

| Component | CHAP-IEM | CHAP-DH |
|-----------|----------|---------|
| Initial key source | Password hash | DH exchange |
| Authentication | Yes (username) | No |
| ID₁ generator | Server | Either party |
| IEM Chain | Yes | Yes |
| Exception recovery key | K (password hash) | K (DH-negotiated) |
| Bidirectional push | Supported | Supported (native) |

---

## VIII. Applicable Scenarios

**Suitable for:**

- IoT scenarios with large numbers of anonymous clients
- Temporary/one-time secure communication
- Server architectures without key tables
- Scenarios needing IEM chain features but not authentication
- Resource-constrained devices (DH modular exponentiation can be precomputed)

**Not suitable for:**

- Scenarios requiring authentication
- Sensitive scenarios requiring MitM attack resistance
- Environments with existing PKI infrastructure

---

## IX. Summary

The core essence of CHAP-DH is:

> **Replace the login phase of CHAP-IEM with DH key exchange, removing all authentication and pre-shared secrets while retaining all security features of the IEM chain.**

**Protocol Hierarchy:**

```
ZIM (Zigzag Interaction Model)
  ├── CHAP (fixed key + ID chain + authentication)
  ├── CHAP-IEM (ID as key + authentication)
  ├── CHAP-IEM-SKN (pre-shared Y + DH mixing + authentication)
  └── CHAP-DH (standard DH + IEM chain + anonymous)
```

**Core Advantages:**

- Zero pre-shared secrets, zero configuration, zero key table
- Completely anonymous, transmits no identity information
- Inherits all IEM features: chained keys, forward secrecy, bidirectional push, exception recovery
- Server maintains only session state, no password table needed
- Zero configuration cost in multi-user scenarios
